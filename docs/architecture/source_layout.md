# Source layout

The service coordinates registered drivers and owns their lifetime. Moving a
method to another translation unit does not transfer its state or ownership.

| Directory | Responsibility |
| --- | --- |
| `CirrusAudioFixup/Service` | IOService entry points, attachment, runtime observation, power callbacks and diagnostic publication |
| `CirrusAudioFixup/Core` | Bus, register, amplifier and lifecycle contracts independent of machine integration |
| `CirrusAudioFixup/Runtime` | Driver registration, amplifier instances and group coordination |
| `CirrusAudioFixup/Platform/ACPI` | ACPI properties, resource parsing, path resolution and metadata publication |
| `CirrusAudioFixup/Platform/Board` | Board identity, discovered wiring and platform profiles |
| `CirrusAudioFixup/Platform/HDA` | Audio events and stream observation |
| `CirrusAudioFixup/Transport/I2C` | I2C controller/provider interfaces and register transactions |
| `CirrusAudioFixup/Transport/SPI` | SPI controller ownership, power client and register transactions, including Intel and AMD implementations |
| `CirrusAudioFixup/Devices/Amplifiers` | Each silicon family's configuration, hardware sequences, firmware policy and playback |
| `CirrusAudioFixup/Firmware` | Shared firmware formats, parsing and upload contracts |

`Service/CirrusAudioFixup.cpp` retains the metaclass and service entry points.
`CirrusAudioFixupAttachment.cpp`, `CirrusAudioFixupRuntime.cpp`,
`CirrusAudioFixupPower.cpp` and `CirrusAudioFixupDiagnostics.cpp` implement the
same class. `CirrusAudioFixupSupport.hpp` contains private adapters and inline helpers.
The command gate, workloop, pending power state and teardown order remain owned
by that service.

The CS35L41 driver follows the same pattern: `CS35L41Driver.cpp` coordinates
lifecycle hooks; `CS35L41Hardware.cpp`, `CS35L41Firmware.cpp`,
`CS35L41Playback.cpp` and `CS35L41Diagnostics.cpp` implement their subsystems.
Board facts stay under `CS35L41/Board`; they do not belong in shared transport
or generic amplifier contracts.

## Embedded resources

`Resources/FirmwareData.hpp` declares the resource table and its count.
`FirmwareData.cpp` includes `Generated/FirmwareData.inc` exactly once. The byte
arrays are private to that translation unit; the table borrows immutable data
for the lifetime of the kext. Firmware remains embedded in the binary.

Use `Tools/Firmware/import_firmware.py` to import matching firmware and tuning.
Its default output is the selected family's `Resources/Generated/FirmwareData.inc`.
Resource selection and the schema remain separate from the generated bytes.

## Tests and tools

Run `python3 Tests/run.py` from the repository root. The runner lists each suite
explicitly. Checks are grouped under `Architecture`, `Build`, `Drivers`,
`Platform` and `Transport`; reusable fixtures live under `Fixtures`. Source
extraction fixtures read all relevant translation units, and the complete
CS35L41 test links the production implementations and embedded resource data.

Build and release helpers are under `Tools/Build`, collectors under
`Tools/Collectors`, importers under `Tools/Firmware`, and reference inspection
utilities under `Tools/Audit`. The collectors remain standalone scripts, with
the Windows launcher and its PowerShell implementation kept together.

Run `bash Tools/Build/build_macos.sh` on macOS for Debug/Release builds and binary
checks. Host tests and target syntax checks do not establish successful kext
loading, audible output or sleep/wake behavior on hardware.

## Naming

The registry is the source of supported driver identities; there is no second
silicon catalog in `Core`. `AmplifierDriverModules.hpp` composes registered
families, and `NativeSPIControllerSelection.hpp` selects controller owners.
Neither composition point authorizes hardware writes.

`CS35L41BoardDiscovery` interprets board properties. `BoardMetadataFallback.hpp`
adds verified missing metadata, while `BoardPropertyCorrections.hpp` describes
known firmware defects. `RuntimeState` includes firmware, playback and recovery;
`InstanceState` adds endpoint bindings. Existing controller names continue to
match their main class. Boot arguments, IORegistry properties, ACPI contracts,
firmware identity and the service metaclass keep their existing names.
